## 1. DNS：IP アドレスをドメイン名に変える仕組み {#1-dns}

### IP アドレスとは

インターネット上の通信は本来、`153.120.x.x` のような**数字の列（IP アドレス）**で行われる。  
人間が覚えるのは難しいので、`circlemanage.jp` のような名前に変換する仕組みが **DNS（Domain Name System）**。

### 「好きなドメイン名」に変える 3 ステップ

```
  Step 1. レジストラ（お名前.com など）で「この名前を使いたい」と申請・購入

  Step 2. ネームサーバー設定
          「このドメインの問い合わせは Cloudflare に聞いてくれ」と
          レジストラに登録する

  Step 3. DNS レコード登録
          Cloudflare 上で「circlemanage.jp にアクセスが来たら
          このラズパイ（トンネル）に繋いで」という名簿を書き込む
```

### DNS 名前解決の流れ

```
  あなたの PC
      |
      +--①「circlemanage.jp の IP は何番？」--->  DNS サーバー
      |                                              |
      +<--②「Cloudflare のサーバー IP だよ」--------+
      |
      +--③ Cloudflare の IP にアクセス！--->  Cloudflare
      |                                              |
      +<--④ ページのデータを返す-------------------+
      |
      v
  Web ページが表示される！
```

| 分野 | 内容 |
|------|------|
| コンピュータネットワーク | DNS・IP アドレス・ルーティングの仕組み |
| 分散システム | DNS は世界中のサーバーが協調して動く分散データベース |

## 2. ドメインの階層構造と practice.circlemanage.jp の謎 {#2-domain}

### ドメインの構造

```
  https://practice.circlemanage.jp

  [プロトコル]  [サブドメイン] [取得したドメイン] [TLD]
     https://     practice  .  circlemanage   . jp
```

| 部分 | 名前 | 説明 |
|------|------|------|
| `.jp` | TLD（トップレベルドメイン） | 国や種類を表す。`.jp` は日本在住者しか取得できない |
| `circlemanage` | SLD（セカンドレベルドメイン） | 自分が購入した独自ドメイン部分 |
| `practice` | サブドメイン | 自分で自由に決められる「枝」 |

### なぜ `practice` になっているのか

参考にした Zenn 記事の手順で、Cloudflare Tunnel を設定する際に **`practice` というサブドメインを指定していたから**。  
記事の著者が「練習用（practice）」として使った名前をそのままなぞった結果。

### `www` に変えたい場合

```
  変更前: practice.circlemanage.jp
  変更後: www.circlemanage.jp
```

**Cloudflare のダッシュボード → Zero Trust → Tunnels → Public Hostname**  
`practice` と書いてある部分を `www` に書き換えるだけ。ドメイン自体の変更は不要。

### このドメインは安全か？

| 観点 | 評価 |
|------|------|
| `.jp` ドメインの信頼性 | 日本在住者しか取得できないため世界的に信頼性が高い |
| `practice` というサブドメイン | 単なる名前。機能やセキュリティに影響しない |
| HTTPS 化 | Cloudflare Tunnel が SSL 証明書を自動発行。通信は暗号化済み |

## 3. OS の役割と RAM / ROM の違い {#3-os-memory}

### OS（オペレーティングシステム）とは

```
  ハードウェア（ラズパイ基板）
       |
  +-----------------+
  |   OS（Ubuntu）   |  <-- ソフトウェアが動く「土台」
  |  Linux カーネル  |
  +-----------------+
       |
  アプリケーション（Nginx, Python など）
```

OS がなければ「LED を光らせる」だけでも電気信号レベルから全部書く必要がある。  
OS が「ファイルを保存する」「ネットワークに繋ぐ」などを抽象化してくれる。

**シェル（ターミナル）** は、OS に人間が文字で命令を出すための「窓口」。  
→ Windows のコマンドプロンプト、Mac のターミナル、Linux の Bash が同じ役割。

### ラズパイで使える主な OS

| OS 名 | 旧称 | 特徴 |
|-------|------|------|
| **Raspberry Pi OS** | Raspbian（ラズビアン） | ラズパイ公式。研究室でよく使われる |
| **Ubuntu Server** | — | 汎用 Linux。今回の Zenn 記事で使用 |
| **Ubuntu Desktop** | — | GUI あり。重いがわかりやすい |

### RAM と ROM の違い

```
  ラズパイの記憶装置

  +------------------------------+   +------------------+
  |   RAM（主記憶装置）           |   |   microSD        |
  |   = 作業机                   |   |   = ROM/ストレージ |
  |                              |   |   = 本棚・倉庫    |
  |  ・読み書き超高速             |   |                  |
  |  ・電源を切ると消える         |   |  ・電源切っても残る|
  |  ・基板にハンダ付け済み       |   |  ・OS を入れる   |
  |  ・4GB / 8GB モデルの「GB」  |   |  ・外付けで交換可 |
  +------------------------------+   +------------------+
```

### 起動時の動作

```
  電源 ON
      |
      v
  microSD（ROM）に保存された OS を読み込む
      |
      v
  OS を RAM（作業机）に展開して起動
      |
      v
  Nginx などのソフトが RAM 上で動作
  データの保存は microSD（ROM）に書き込む
```

## 4. Linux コマンドの正体（sudo・apt など） {#4-linux-commands}

これらは「プログラミング言語」ではなく、**OS（Linux）に命令を出すためのシェルコマンド**。  
打ち込む場所（ターミナル）で動いている仕組みを **Bash（バッシュ）** と呼ぶ。

### よく出てくるコマンド一覧

| コマンド | 意味 | 例え |
|---------|------|------|
| `sudo` | SuperUser DO。管理者権限で実行 | Windows の「管理者として実行」 |
| `apt` | Advanced Package Tool。パッケージ管理 | スマホの「アプリストア」 |
| `apt install` | ソフトをインストール | アプリストアで「入手」ボタン |
| `apt update` | インストール可能なソフトのリストを更新 | アプリストアの「更新確認」 |
| `systemctl` | サービス（常駐ソフト）の起動・停止・確認 | タスクマネージャー |
| `ls` | ファイル一覧を表示 | エクスプローラーで中身を見る |
| `cd` | ディレクトリ（フォルダ）を移動 | エクスプローラーでフォルダを開く |
| `cat` | ファイルの中身を表示 | メモ帳でファイルを開く |
| `nano` / `vim` | ファイルをターミナル上で編集 | ターミナル版メモ帳 |

### `sudo apt install nginx` を分解すると

```
  sudo          apt           install       nginx
    |             |               |            |
  管理者権限で  パッケージ管理   インストール  Nginx という
  実行してね    ツールを使って   してね       ソフトを
```

### コマンドは「言語」か？

正確には Bash（シェル）という「スクリプト言語」で書かれたコマンド群。  
Python とは別物だが、`for` ループや `if` 文も書けるれっきとした言語。

## 5. HTTP vs HTTPS：なぜ内部は HTTP で OK なのか {#5-http-https}

### プロトコルとは

通信のルール・取り決めのこと。「どんな形式でデータをやり取りするか」を決める。

### HTTP と HTTPS の違い

| 項目 | HTTP | HTTPS |
|------|------|-------|
| 暗号化 | なし（平文） | あり（TLS/SSL） |
| 盗聴リスク | 第三者が中身を読める | 暗号化されているので読めない |
| 用途 | 内部通信・閉域網 | インターネット経由の通信全般 |
| 速度 | 高速 | 暗号化処理の分だけ若干遅い |

### 今回の構成での使い分け

```
  【外の世界（インターネット）】
  ユーザー <----HTTPS（暗号化）----> Cloudflare
                                        |
  【Cloudflare Tunnel 内部（仮想的に安全）】
                                        |
                                   トンネル（暗号化済み）
                                        |
  【ラズパイの中（ローカル）】            |
                                   cloudflared
                                        |
                                   HTTP（暗号化なし）
                                        |
                                      Nginx
```

ラズパイ内部では「自分の機械の中だけ」なので盗聴される心配がない。  
→ 内部は HTTP でも問題なし。外に出る時だけ HTTPS で暗号化。

## 6. MQTT とは何か（HTTP との違い） {#6-mqtt}

### MQTT（Message Queuing Telemetry Transport）

センシング・IoT 分野でよく使われる軽量な通信プロトコル。

### HTTP との通信スタイルの違い

```
  【HTTP：一問一答型（Request / Response）】

  クライアント ---「データちょうだい」---> サーバー
  クライアント <--「はいどうぞ」---------- サーバー

  問題: センサが「今、異常が起きた！」と自発的に報告するのが苦手
        常にサーバー側から聞きに行く必要がある（ポーリング）

  ─────────────────────────────────────────────────────────

  【MQTT：掲示板型（Publish / Subscribe）】

  センサ（Publisher）  ---データを投稿--->  Broker（掲示板）
  PC（Subscriber）     <--データを受け取る-  Broker（掲示板）

  利点: センサが変化した瞬間に通知できる
        データサイズが小さく、低電力・不安定な環境に最適
```

### 使い分けの目安

| ユースケース | 向いているプロトコル |
|------------|------------------|
| Web アプリのデータ取得 | HTTP / HTTPS |
| スマート農業センサの通知 | MQTT |
| リアルタイムの IoT 監視 | MQTT |
| REST API | HTTP |

| 分野 | 内容 |
|------|------|
| コンピュータネットワーク | アプリケーション層（L7）のプロトコル設計 |
| 組み込みシステム | 低リソース環境での通信設計 |

## 7. ネットワークセキュリティ：閉域 vs 公開の設計思想 {#7-security}

### 「安全」の定義はシステムの目的によって変わる

```
  【閉域システム（学部の HaLow 研究）】      【公開システム（今回のサーバー）】

  外の世界 ---X--> ルーター ---> LAN 内        外の世界 ----> Cloudflare ----> ラズパイ
                                               （全世界からアクセス可能）
  物理的な壁で外部を遮断                       数学的な暗号化で内部を保護
  = エアギャップに近い状態                     = ゼロトラストの考え方
```

### エアギャップとは

外部ネットワークと物理的に切り離された状態。  
接続口がそもそも存在しないため、インターネット越しの攻撃は届かない。  
→ 原子力施設・軍事システムなどでも使われる最強の防御。

### 閉域システムの残る脆弱性

閉域でも「同じネットワーク内に悪意のある人がいた場合」はリスクがある。

| 攻撃手法 | 内容 | 対策 |
|---------|------|------|
| パケットキャプチャ | 同一 LAN 内の通信を盗聴する | 通信を暗号化する（HTTPS・TLS） |
| なりすまし | 偽の命令パケットを送る | 認証・署名を入れる |
| Wi-Fi 傍受 | 無線の電波を傍受する | WPA3 など強い暗号化方式を使う |

### ゼロトラストとは

「何も信用しない、常に検証する」というセキュリティの考え方。  
「同じネットワーク内だから安全」という前提を捨て、すべての通信を検証する。

```
  旧来の考え方（境界防御）: 外の敵を壁でブロックすれば内部は安全
  ゼロトラスト:            内部でも外部でもすべての通信を都度認証・暗号化
```

### システム目的別のセキュリティ設計

| システム | 信頼モデル | 対策の方向性 |
|---------|-----------|------------|
| 学部の HaLow 研究 | 物理的閉域を信頼 | ルーターで外部遮断、LAN 内に敵がいない前提 |
| 今回の Web アプリ | 何も信頼しない | HTTPS 暗号化 + Cloudflare でフィルタリング |

## 8. 学部時代の Wi-Fi HaLow システムの仕組み分析 {#8-halow}

### システム構成の全体像

```
  【屋外エリア】                          【屋内エリア】

  センサ・アクチュエーター                   ラズパイ（制御PC）
       |                                        |
  ホテルルーター（Wi-Fi AP）                    |
       |                                        |
  Wi-Fi HaLow 子機 -----(長距離無線)-----  Wi-Fi HaLow 親機
```

### なぜ「プライベート IP の壁」を越えられたのか

**仮説：HaLow 親子機が L2 ブリッジとして動作していた**

```
  L2 ブリッジ（透明な長いケーブル）のイメージ:

  ラズパイ -----(仮想的に同じ LAN)------ センサ

  ↑ IP アドレスレベルでは「同じネットワーク内の隣人」として見える
    = プライベート IP の壁が存在しない
```

HaLow の親子機が「橋（ブリッジ）」として機能し、  
屋内のラズパイと屋外のセンサが物理的に離れていても「同じ LAN」として振る舞った。

### ホテルルーターをいじった理由（推測）

もしホテルルーターが「ルーターモード」（IP アドレスを別途割り振る設定）だった場合、  
二重ルーター状態になってしまい通信が届かなかった可能性がある。

```
  二重ルーター問題:

  ラズパイ（192.168.1.x）
       |
  HaLow 親機ルーター（192.168.1.1）  <-- ここで通信が止まる
       |
  ホテルルーター（192.168.2.1）       <-- 別のネットワーク
       |
  センサ（192.168.2.x）
```

解決策として「ホテルルーターをブリッジモード（AP モード）に変更」した可能性が高い。  
→ ホテルルーターが IP を割り振るのをやめ、HaLow 親機の LAN に統合される。

### Cloudflare Tunnel との比較

| 項目 | 学部の HaLow システム | 今回の Cloudflare サーバー |
|------|---------------------|--------------------------|
| 通信範囲 | HaLow で繋がった閉域 LAN 内 | 全世界（インターネット） |
| IP の種類 | プライベート IP 同士で完結 | グローバル IP からの接続 |
| 壁の越え方 | HaLow で物理的に「橋」を架ける（L2） | Cloudflare で仮想的に「トンネル」を掘る（L7） |
| セキュリティ | 物理的な閉域で遮断 | 暗号化で保護 |
| 解決する層 | データリンク層（L2） | アプリケーション層（L7） |

### ネットワーク階層（OSI モデル）との対応

```
  L7  アプリケーション層  HTTP / HTTPS / MQTT    <-- Cloudflare Tunnel が動く層
  L6  プレゼンテーション層
  L5  セッション層
  L4  トランスポート層    TCP / UDP
  L3  ネットワーク層     IP アドレス             <-- ルーターが動く層
  L2  データリンク層     MAC アドレス            <-- HaLow ブリッジが動く層
  L1  物理層            電波・光・電気信号        <-- HaLow の無線
```

HaLow システム（L2）は「IP アドレスより下の層」で橋を架けたので、  
IP の概念を超えて「同じ LAN」として見えた。これが動いた理由。
